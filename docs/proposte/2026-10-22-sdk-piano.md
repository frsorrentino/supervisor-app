## In cinque righe

1. L'Agent SDK (`@anthropic-ai/claude-agent-sdk`, `claude-agent-sdk`) è Claude Code come libreria: stessa CLI, stesso agent loop, ma con eventi strutturati, una callback per permessi e domande, hook in-process, `interrupt()`, `setModel()`, `setPermissionMode()`, ripresa e biforcazione delle sessioni. Tutto quello che oggi il relay ricava dallo schermo tmux e dalle trascrizioni `.jsonl` (formato dichiarato interno e instabile) diventa un flusso di messaggi tipizzati.
2. Le sessioni restano sul PC con file, `CLAUDE.md`, memorie, skill, plugin e MCP: l'SDK li carica dalle stesse cartelle della CLI (`settingSources` predefinito `user`, `project`, `local`; auto memory inclusa).
3. Si perde il link Remote Control (claude.ai/code) per le sessioni ospitate dall'SDK, i comandi solo-terminale e, in preview, i channel. Tmux e SDK devono convivere: la migrazione è per sessione, non a scatto.
4. Accesso: Franz sulla sua macchina può usare il suo abbonamento (il binario non modificato con il login di Claude Code); un prodotto pubblico non può far passare le richieste dal suo Pro/Max né raccogliere credenziali claude.ai: ogni utente entra con il proprio abbonamento tramite il flusso di Anthropic, o con la propria API key.
5. Le funzioni nuove di più valore: permessi e domande dal telefono senza scraping (con anteprime), lettura dal vivo del testo mentre nasce, Modifiche esatte dagli hook, costo e contesto per turno, Annulla di una modifica (checkpoint), subagent e lavori in sottofondo visibili, un server MCP di supervisor che apre il PC all'app Claude, a claude.ai e a Duet.

## 2. Accesso e termini: abbonamento o API key

Testo esatto della pagina [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) (letta il 22/10/2026, la pagina non riporta una data), sezione «Authentication and credential use»:

> **OAuth authentication** is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications.
>
> **Developers** building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow.
>
> This does not restrict how customers provision and manage their own API keys […]. Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code as described under *Can customers offer Claude Code in their products?* above.

E, sezione «Can customers offer Claude Code in their products?»:

> The Claude Code binary must not be modified. […] customers may not remove, disable, or restrict any authentication method built into it (including methods that permit signing in with a Claude account or the user's own API key).
> Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential […]. That usage is billed directly to the end user.

Sezione «Acceptable use»: «Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK.»

La [panoramica dell'SDK](https://code.claude.com/docs/en/agent-sdk/overview) ripete: «Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead.»

Cosa ne segue.

- **Franz sulla sua macchina.** L'ospite SDK avvia il binario non modificato di Claude Code, che legge il login fatto con `/login` nella `CLAUDE_CONFIG_DIR` dell'account (precedenza delle credenziali: [Authentication](https://code.claude.com/docs/en/authentication#authentication-precedence)). È «un utente finale che entra nel binario non modificato con il proprio abbonamento»: uso ordinario e individuale, consumo sulle finestre del piano come oggi. L'alternativa `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN` autentica con l'abbonamento ma «can only make model requests»: niente connettori claude.ai, e `--bare` non lo legge.
- **Prodotto pubblico.** Supervisor non può far passare le richieste di altri dal Pro/Max di Franz, né mostrare un proprio login claude.ai, né conservare token. Può: avviare il binario non modificato sul PC dell'utente e lasciare che l'utente faccia `claude /login` da solo (il flusso di Anthropic), oppure usare la sua API key (`ANTHROPIC_API_KEY`, a consumo, listino API). Sul telefono quindi: nessun campo credenziali di Claude, mai; il primo avvio dice «apri un terminale ed esegui `claude`, poi torna qui».
- **Prezzo per l'utente.** Con l'abbonamento: incluso nel suo piano, limiti del piano. Con la API key: pagato a token al listino (Opus 5.5 4 $/20 $ per milione, Sonnet 5.5 2 $/10 $); `maxBudgetUsd` diventa un vero tetto. Remote Control resta solo con l'abbonamento.
- **Posizionamento.** Supervisor è «un client per le proprie sessioni Claude Code», non «Claude in un'altra app»: il binario, il login e la fattura sono dell'utente. Il marchio: si può dire che «runs Claude Code», non usare nome e logo come parte del prodotto.

## 3. Com'è oggi e come sarà

**Oggi.** Ogni sessione è una CLI interattiva in una finestra tmux. Il relay (Python, plugin `team-supervisor`) legge lo schermo con `capture-pane` (stato, `tool`, contesto, «ti aspetta»), legge le trascrizioni `~/.claude/projects/*/*.jsonl` (chat, esito, domande), scrive con `send-keys` (prompt, risposte numerate, Esc per `interrupt`, `/model`, `/effort`, modalità dei permessi), e pubblica stato, eventi e trascrizioni cifrati su Firebase RTDB; l'app manda comandi (`ops`: `answer`, `prompt`, `launch`, `interrupt`, `model`, `effort`, `permission_mode`, `transcript`, `changes`, `diff`, `approve`, …) e riceve i risultati. Fragilità: lo schermo cambia con ogni versione della CLI, il `.jsonl` è dichiarato instabile, la risposta a una domanda è una sequenza di tasti, i permessi si vedono solo quando il dialogo è a schermo, il costo non si vede.

**Domani.** Un **ospite** («cc-host», un processo per macchina: Chromebook e win) avvia ogni sessione con `query()` in streaming e tiene aperta la coda dei messaggi. L'ospite traduce i messaggi dell'SDK in eventi strutturati per il relay (stesso bus RTDB, stesso cifrario, contratto esteso) e i comandi dell'app in chiamate: prompt → messaggio utente in coda, risposta a domanda → ritorno della `canUseTool`, permesso → `allow`/`deny`/`updatedPermissions`, Stop → `interrupt()`, modello → `setModel()`, modalità → `setPermissionMode()`, riapri → `resume`. Tmux resta per le sessioni che Franz vuole aprire anche da claude.ai (Remote Control) o a cui serve un canale.

| | Oggi (tmux + trascrizioni) | Con l'ospite SDK |
|---|---|---|
| Stato della sessione | Dallo schermo: fragile, in ritardo | `init`, `assistant`, `user`, `result`, `status`, `task_*`: esatto e immediato |
| Testo di Claude | Dalla trascrizione, a turno finito | `stream_event` lettera per lettera, poi il messaggio intero |
| Domande | Dalla trascrizione e dallo schermo; risposta con tasti | `AskUserQuestion` nella callback: domande, opzioni, multiSelect, anteprime; risposta tipizzata, anche libera |
| Permessi | Visibili solo nel dialogo a schermo | Ogni richiesta nella callback, con `suggestions` per «ricorda»; `PreToolUse` per regole proprie; `defer` per le attese lunghe |
| Stop, modello, effort, modalità | Tasti e slash | `interrupt()`, `setModel()`, `effort`, `setPermissionMode()` con conferma |
| Modifiche | `git diff` sul repo | `PostToolUse` su Write/Edit (`file_path`, `old_string`, `new_string`) più `git diff` per Bash |
| Costo, contesto, quota | Niente / dallo schermo | `result.total_cost_usd`, `modelUsage`, `getContextUsage()` (percentuale e categorie), `status: compacting`, `compact_boundary`, `rate_limit_event` (finestre 5 h e 7 g) |
| Subagent e sottofondo | Invisibili | `task_started`/`task_progress`/`task_notification`, `SubagentStart`/`Stop` |
| Riapertura | `claude --resume` in tmux | `resume: id`, `forkSession`, `listSessions()`, `getSessionMessages()` |
| Remote Control | C'è | Non c'è (solo tmux) |

Linguaggio dell'ospite: il relay è Python e il `claude-agent-sdk` basta per il grosso; il TypeScript ha il set completo di hook (`SessionStart`/`End`, `PostToolBatch`, `PermissionDenied`, `PreCompact`/`PostCompact`, `Elicitation`), `getContextUsage()`, `accountInfo()` e le anteprime delle domande. Proposta: ospite in TypeScript come processo a parte, con un socket locale verso il relay Python; il relay resta il padrone del bus e del contratto. La sessione supervisor decide.

## 4. Sezione per sezione dell'app

Per ogni sezione: cosa cambia, cosa migliora, cosa si perde, come si migra. Vale per telefono, tablet, web e orologio dove non detto altrimenti.

**Home (riepilogo, «Ti aspettano», banner).**
- Cambia: lo stato arriva dagli eventi (`status`, `result`, `permission_prompt`, `task_*`), non dallo schermo. «Ti aspetta» = una `canUseTool` in sospeso o un `tool_deferred`.
- Migliora: zero ritardi e zero falsi «al lavoro»; il banner sa *cosa* aspetta (permesso, domanda, elicitation MCP) e da quanto; «Ha finito» coincide con il `result`.
- Si perde: niente.
- Migrazione: i campi del contratto restano; si aggiunge `host: "tmux"|"sdk"` per sessione e `waiting_kind`. L'app non cambia finché il relay non alza la versione.

**Sessioni (card, Riapri, Chiudi, segui).**
- Cambia: lancio = `query()` con `cwd`, `model`, `effort`, `permissionMode`, `plugins`, `settingSources`; chiusura = fine dello stream; riapertura = `resume`; «ramo» = `forkSession`.
- Migliora: `init` dà modello, tool, MCP, plugin, skill e comandi davvero caricati (oggi dedotti); `listSessions()` elenca le chiuse riapribili con titolo e tag; `renameSession()`/`tagSession()` dal telefono.
- Si perde: il link claude.ai della sessione (Remote Control). «Apri in supervisor» prende il suo posto.
- Migrazione: `launch` ottiene `host` (tmux o sdk); il relay tiene la mappa nome → `session_id` SDK.

**Chat (feed, invio, ▶, copia).**
- Cambia: il testo di Claude arriva in streaming (`text_delta`) e i tool call come blocchi `tool_use`/`tool_result` tipizzati; la storia da `getSessionMessages()` invece del `.jsonl`.
- Migliora: lettura dal vivo mentre scrive (anche la voce può partire a fine frase); le righe «Esito:» e «Prossimi:» si estraggono dal messaggio intero, non da righe di schermo; immagini e file allegati come blocchi `image` nel messaggio utente (streaming input); `interrupt()` esatto.
- Si perde: nulla di funzionale; l'op `transcript` cambia sorgente.
- Migrazione: `transcript`/`tail` servono lo stesso formato riempito dagli eventi; nuovo evento `delta` opzionale nel contratto per il testo dal vivo (il bus RTDB va dimensionato: un delta ogni ~300 ms, non uno per token).

**Modifiche (`changes`, `diff`).**
- Cambia: `PostToolUse` su Write/Edit/NotebookEdit dà file e sostituzione esatta per turno; `git diff` resta per quello che passa da Bash.
- Migliora: «cosa ha toccato questo turno» per file, con il vecchio e il nuovo testo; «Annulla» via `rewindFiles()` (checkpoint) dal telefono.
- Si perde: l'Annulla non copre Bash né i subagent.
- Migrazione: `changes` ottiene `turn_edits[]`; nuova op `rewind` (solo sessioni SDK).

**Domande e permessi (QuestionCard, Permessi, «allow_all», modalità).**
- Cambia: la domanda è il JSON di `AskUserQuestion` (titolo, opzioni, `multiSelect`, anteprima html/markdown); il permesso è `toolName` + `input` (per Bash il comando, per Write il file e il contenuto) + `suggestions`.
- Migliora: risposte multiple e libere senza trucchi di tastiera; «Consenti e ricorda» scrive la regola in `settings.local.json`; «Consenti con modifica» cambia il comando prima di eseguirlo; «Suggerisci alternativa» manda un testo a Claude; cambio di modalità con conferma (`setPermissionMode`) e stato vero (`status.permissionMode`); le anteprime delle opzioni (mockup di layout) si vedono sul telefono.
- Si perde: la trust del progetto e il consenso ai server MCP restano dialoghi solo-terminale (l'SDK non li fa: si risolvono al lancio con `settings`/`.mcp.json` approvati).

- Migliora: l'agenda del recap conosce le sessioni SDK come le altre.
- Migrazione: nessuna.

## 6. Le due domande di stasera

### 6a. Una master «sul telefono» che comanda le sessioni del PC con memorie e plugin

Quattro strade, tutte con le sessioni sul PC.

1. **Remote Control della master (oggi).** `claude --rc` sulla master; dall'app Claude si scrive, si risponde a domande e permessi, si cambia modello ed effort; richiede l'abbonamento, non la API key. È quello che Franz usa già; il limite è che l'app Claude non sa niente delle altre sessioni. [Remote Control](https://code.claude.com/docs/en/remote-control)
2. **Telegram come canale della master (subito, zero codice).** `claude --channels plugin:telegram@claude-plugins-official` sulla master in tmux: i messaggi del bot entrano nella sessione (con memorie, plugin, hook), le risposte tornano in chat, i permessi si approvano con «yes abcde» (permission relay). Research preview, serve Bun, allowlist dei mittenti, solo sessioni interattive. Franz ha già Telegram per supervisor. [Channels](https://code.claude.com/docs/en/channels)
3. **La master nell'app supervisor via SDK (questo piano).** La master gira nell'ospite SDK con `settingSources` e `plugins` del PC; il telefono è il suo client completo attraverso il relay. È la strada che rende l'app il «terminale» della master. Costo: la master perde il link claude.ai.
4. **La master dentro l'app Claude via connettore MCP (sezione 7).** Una chat di claude.ai (o Duet) con il connettore «supervisor» può elencare, leggere e comandare le sessioni del PC, ma non *è* la master del PC: ha la memoria dell'account Claude, non quella della cartella. Può però parlare alla master vera (`talk master "…"`) e leggere i suoi esiti.

Consiglio: 2 oggi stesso come prova (un'ora), 3 come destinazione, 1 finché serve claude.ai, 4 per Duet e per chi non ha l'app supervisor.

## 7. Il server MCP remoto di supervisor davanti al relay

Un piccolo server HTTPS su `supervisor.francescosorrentino.com/mcp` (o accanto alla PWA), che parla con il relay sullo stesso bus cifrato dell'app, con OAuth.

**Strumenti di lettura** (senza conferma): `sessions_list` (stato, tool, contesto, account, host), `session_tail` (coda dell'output di una sessione, N righe), `waiting` («Ti aspettano»: domande, permessi, ferme per te), `commitments` (Impegni del registro, con età e prossimo passo), `quota` (5 h e settimana per account), `night_report` (ultimo rapporto, o per giorno).

**Strumenti di scrittura** (ogni chiamata chiede conferma sul telefono prima di eseguire: il server la mette in `state.attention` e aspetta l'ok dall'app supervisor, come un `canUseTool`): `session_prompt` (prompt a una sessione), `session_answer` (risposta a una domanda o a un permesso), `approve` (ok a un compito del registro), `session_launch` (apri una sessione in una cartella), `session_close`. Su claude.ai si può in più impostare per strumento «Needs approval» o «Blocked».

**Sicurezza.** OAuth con client registrato da Franz («Use your own OAuth client»), un solo account autorizzato, token a vita breve; ogni scrittura confermata dal telefono con il testo intero della richiesta; log di tutte le chiamate come eventi del relay; niente segreti nei risultati (i tool leggono i testi che l'app già riceve, già filtrati); rate limit; chiusura del server a un tocco dall'app. Il server non tocca tmux né l'SDK: parla solo con il relay, come l'app.

**Marketplace.** Per uso personale basta il custom connector (nessuna revisione). La directory serve se supervisor diventa un prodotto: in quel caso ogni utente avrebbe il *suo* server (gira sul suo PC o sul suo dominio) e il connettore pubblicato dovrebbe essere parametrico sull'URL, che la directory ammette («Some connectors first ask for details such as a server URL»); revisione di Anthropic con i criteri di `review-criteria`. Candidatura sensata solo dopo il primo avvio per utenti terzi (sezione 9).

**Cosa sblocca.** Duet che ogni poche ore legge `waiting` e `commitments` e avvisa Franz di un ok fermo da due ore (P3 senza scrivere un hook); l'app Claude come master di riserva; claude.ai sul PC di un altro come vista delle sessioni.

## 10. Rischi e limiti

- **Riprendere al PC senza terminale.** Una sessione SDK non è nel picker; si apre con `claude --resume <id>`, ma due processi sulla stessa sessione intrecciano i messaggi. Serve un «passamano»: l'app chiede `release`, l'ospite chiude il suo `query()` (`interrupt()` + fine dello stream), stampa il comando, e quando Franz esce dal terminale l'ospite riprende con `resume`. Da progettare nel contratto.
- **Funzioni del terminale che mancano.** Remote Control, `/login`, picker, statusline, mod, agent teams, canali propri, trust della cartella e consenso MCP: le ultime due vanno fatte una volta dalla CLI o con `settings`.
- **Host win.** L'ospite deve girare anche su win (sessioni dove stanno i file); due ospiti, un relay. Il win è condiviso e carico (Bluey): l'ospite va leggero e con `maxBudgetUsd`/`maxTurns` per i lavori notturni.
- **Due account.** Un ospite, una `CLAUDE_CONFIG_DIR` per sessione passata in `env` (TypeScript sostituisce l'ambiente: va ricopiato `process.env`). Le quote restano separate e non lette dall'SDK.
- **Sicurezza.** Il telefono diventa l'approvatore dei permessi: ogni `allow` va mostrato intero (comando, file) e loggato; `updatedPermissions` scrive regole durature, meglio solo su conferma esplicita; l'ospite espone solo il socket locale; il server MCP (sezione 7) è l'unica porta da internet e passa da OAuth e conferma. I subagent ereditano `bypassPermissions` solo se la sessione madre ce l'ha: non usarlo.
- **Quota.** Con l'abbonamento i costi dell'SDK sono stime; la quota si legge da `rate_limit_event` (non documentato); con la API key è a consumo e `maxBudgetUsd` è reale. I lavori notturni in `auto` o `acceptEdits` consumano senza nessuno che guardi: tetto obbligatorio.
- **Preview e versioni.** Channel e agent view sono research preview; gli hook e i messaggi dell'SDK cambiano con le versioni (molte note «requires v2.1.2xx»); l'ospite deve dichiarare la versione minima e leggerla dall'`init`.
- **Termini.** Un prodotto pubblico non può toccare le credenziali claude.ai né instradare sul Pro/Max di Franz; il login resta nel binario; il nome «Claude Code» non entra nel nome del prodotto.
